# 项目经历模板

> 这是给你自己填的模板，不是可以直接发布的文案。
> 规则：只写真实做过的事；量化数字必须有据可查；客户名默认脱敏；没有的项直接删掉，不要编。

## 写法建议

一条项目经历建议控制在 5–8 行，结构固定：

1. **背景**：什么行业、什么规模、为什么要做这次评估
2. **我的角色**：负责范围、执行、报告中的哪部分
3. **方法**：用了哪些阶段/手法，不必写具体 payload
4. **结果**：发现了什么级别的问题、验证到什么程度
5. **改进**：客户采纳了什么，或自己复盘出什么

## 模板

### [行业] 红队评估 / 渗透测试

- **周期**：[YYYY.MM – YYYY.MM]，[X] 人天
- **角色**：[独立执行 / 带队 / 负责 Web 与内网]
- **授权范围**：[X] 个域名、[X] 个应用、[X] 个网段
- **目标**：验证 [边界防护 / 检测响应 / 数据保护] 能力
- **方法**：外部侦察 → 初始访问 → 权限提升 → 横向移动 → 目标达成 → 清理与报告
- **结果**：确认 [高危 X 个 / 中危 X 个]，验证到 [权限层级 / 目标资产]
- **交付**：报告 [X] 份，含复现步骤、影响说明、修复建议
- **复盘**：[检测覆盖的盲区 / 流程上可以改进的点]

## 常见问题

- **数字对不上**：报告里写 3 个高危，简历写 5 个，面试一问就露馅
- **只写结果不写过程**：面试官更关心你怎么确认影响范围，而不是扫出多少条
- **泄露客户信息**：除非客户书面同意，不要写客户名、域名、内网地址
- **把工具当能力**：写"用 X 工具扫出"没有价值，写"如何判断误报、如何验证影响"才有

## 需要长期维护的记录

建议在私有仓库里维护一份 `engagement-log.md`，每次项目结束补三行：

```
YYYY-MM-DD | 行业 | 范围规模 | 最高权限 | 高危数 | 复盘一句话
```

写简历时从这里取真实数据，比回忆可靠。
